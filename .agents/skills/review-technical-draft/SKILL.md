# 기술 원고 리뷰

검토 대상 원고를 보존하고, 독자가 잘못 이해하거나 재현에 실패할 수 있는 부분을 근거와 함께 설명하는 보고서를 만든다. 원문 작성·수정까지 요청받았다면 리뷰와 구분해 해당 작업 절차를 적용한다. 저장소에 `tech-blog-writing`이 있으면 작성·수정에는 그 스킬을 사용한다. 리뷰 요청만으로 원문을 고치거나 글쓰기 체크포인트를 시작하지 않는다.

## 대상과 맥락 파악

- 원고 전체를 UTF-8로 읽고 줄 번호를 확보한다. 한국어가 깨지면 파일 손상이라고 판단하기 전에 읽기·출력 인코딩을 확인한다.
- 관련 기획서·개요·실행 기록·예제 노트북에서 독자 수준, 문체, 기준 버전, 선행 편의 준비 코드를 확인한다. 모든 주변 파일을 무조건 읽지 않는다.
- 작성 과정의 결정 기록(`status.md` 등)이 있으면 관련 결정을 읽는다. 이미 결정된 사항을 같은 근거로 다시 지적하지 않는다. 새 근거로 재검토가 필요하면 기존 결정과 새 근거를 밝히고 ‘결정 재검토 요청’으로 따로 보고한다.
- 기존 리뷰는 선호하는 보고서 형식과 반복되는 문제를 찾는 자료로 활용한다. 과거의 지적이나 버전 값을 현재 원고의 사실로 그대로 가져오지 않는다.
- 라이브러리·API 사용법 원고라면 [사용법 원고 점검 항목](references/usage-checkpoints.md)을 읽는다. 원고의 코드와 관련 있는 항목만 확인하고, 다른 유형의 글에는 강제하지 않는다.
- 한국어 표현은 [한국어 정오표](../../../docs/writing/korean-errata.md), 글 구조는 [안티패턴](../../../docs/writing/anti-patterns.md)에서 관련 유형을 확인해 지적에 기존 유형 번호(예: K3, AP18)를 붙일 수 있다. 맞는 유형이 없으면 억지로 분류하거나 번호를 만들지 않는다. 번호를 붙일 때는 해당 규칙 파일을 링크한다.
- 두 규칙 파일의 적용 원칙을 따른다. '찾는 방법'은 후보를 찾는 단서이고, 실제로 생길 오해를 설명할 수 있을 때 지적한다.
- 정오표의 "지적되었지만 고치지 않은 것"은 적용 범위 안에서 같은 문맥과 같은 근거로 다시 지적하지 않는다. 문맥이 달라졌거나 새 근거가 있으면 기존 결정과 달라진 조건을 밝히고 '결정 재검토 요청'으로 보고한다.
- 두 규칙 파일은 원고를 고친 뒤 Claude 쪽의 writing-rules-update 스킬로 갱신한다. 리뷰 요청만으로는 수정하지 않는다. 기존 유형에 맞지 않지만 반복될 만한 지적은 각 규칙 파일의 절차에 따라 보고서의 "정오표 새 유형 후보"나 "안티패턴 새 유형 후보"에 따로 모은다.

## 검토 기준

내용과 코드를 함께 읽고 아래에서 실제로 관련 있는 항목을 확인한다.

- **설명과 예제의 일치:** 코드가 반환하는 객체, 출력 수치·라벨, 변경되는 변수와 그대로인 변수가 서술과 일치하는가.
- **주장의 범위:** 예제에서 맞는 설명이 무조건적인 규칙으로 확대되었는가. 기본값과 불변 규칙, 반환값과 원본 변경, 라벨과 위치를 혼동하는가.
- **재현 조건:** 버전·백엔드·자료형·선행 셀에 따라 달라지는 동작인가. 다른 위치에 이미 있는 준비 안내를 중복 요구하지 않는다.
- **해석의 타당성:** API 사용법이 통계적 판단이나 인과적 결론을 보장하는 것처럼 서술하는가. ‘더 자주 쓴다’, ‘의미가 없다’, ‘비율이 낮으니 괜찮다’ 등의 주장은 근거와 목적을 확인한다.
- **한국어:** 수식 대상, 지시어, 변수의 대상, 행·값·라벨의 구분이 명확한가. 기존 설명체와 용어를 존중하고 취향 차이를 오류로 취급하지 않는다.
- **Markdown:** 표 안의 파이프 이스케이프, 코드 펜스, 링크 경로·절 제목을 확인한다. 문법 검사와 실제 렌더링 확인을 구분한다.

가능한 모든 예외를 나열하지 않는다. 초보자를 위한 타당한 단순화는 유지하고, 현재 문장 때문에 생길 구체적인 오해가 있을 때 조건을 보완한다. 다른 옵션의 존재만으로 기본 호출 설명을 오류로 분류하지 않는다.

## 근거와 검증

- 동작을 지적하기 전에 기준 버전의 공식 문서나 실제 실행으로 확인한다. 기술적 주장은 공식 문서·소스·원 논문을 우선한다. 외부 자료를 사용하면 관련 지적 가까이에 직접 링크한다.
- 코드와 저장된 출력을 대조할 수 있으면 관련 검증 도구를 사용한다. 기존 블록 검사 스크립트가 있으면 먼저 동작과 한계를 파악한다.
- ‘저장된 로그에 문자열이 포함됨’, ‘해당 노트북 셀의 기록과 일치함’, ‘새 환경에서 재실행함’은 서로 다른 증거다. 어느 수준인지 보고서에 명시한다. 블록 수는 추측하지 말고 직접 센다.
- 예제 실행은 파일 쓰기·네트워크 사용 등 부수효과를 확인한 뒤 한다. 노트북에 저장된 원본 출력은 검증 과정에서 임의로 덮어쓰지 않는다. 필요한 재실행은 복사본이나 별도 출력 경로를 사용한다.
- 실행 환경이 없으면 이용 가능한 기존 환경을 확인하고, 문서·기록으로 검증할 수 있는 작업을 계속한다. 재실행하지 않았다는 사실과 남은 불확실성을 밝힌다. 단순 리뷰를 위해 의존성 설치나 전체 사이트 빌드를 자동으로 추가하지 않는다.
- 기준 버전과 다른 환경에서 실행한 결과는 버전에 따라 달라지는 동작의 근거로 쓰지 않는다. 실행 버전을 밝히고 ‘기준 버전 확인 필요’로 표시한다. 기준 버전의 공식 문서·소스·실행 기록으로 확인했다면 그 근거를 별도로 제시하며, 다른 버전에서의 실행을 기준 버전 재현으로 표현하지 않는다.
- 보고서에 제안한 코드를 실행하지 않았다면 실행된 결과처럼 표현하지 않는다. 불확실한 문제는 확인 필요로 표시하거나 보고서에서 제외한다.
- 수정안 자체도 검증한다. 원문보다 단정을 넓히지 않았는지, 같은 원고의 앞선 예제가 반례가 되지 않는지 확인한다. 동작을 주장하는 수정안은 기준 버전의 근거와 대조하고, 확인된 범위를 넘으면 조건을 붙이거나 표현을 좁힌다. 표·본문·요약 사이에서도 이 범위가 일치해야 한다.

## 보고서 작성

사용자가 경로를 지정하지 않으면 원고와 같은 폴더에 저장한다. `cN-01-body.md` 형태는 `cN-01-review.md`, 그 외에는 `<원고 stem>-review.md`를 기본으로 한다. 기존 보고서가 있으면 먼저 읽고, 새 검토인지 기존 보고서 갱신인지 요청 맥락을 따른다.

보고서는 한국어 Markdown으로 작성하고 다음 정보를 필요에 맞게 구성한다. 빈 섹션이나 고정된 지적 개수는 만들지 않는다.

1. 대상 링크, 검토일, 범위, 줄 번호 기준, 원문 수정 여부.
2. 종합 판단: 중요한 오류와 실제 영향을 먼저 설명한다.
3. 내용상 지적: 위치·짧은 원문·문제의 이유·문체에 맞는 수정안·근거.
4. 한국어 표현 개선: 비교하기 쉬우면 위치/원문/제안/이유 표를 사용한다.
5. 선택적 보완: 현재 내용은 맞지만 도움 되는 설명만 별도로 둔다.
6. 검증 결과와 한계: 수행한 검사, 실행 여부, 확인하지 못한 사항.

**분류:** 명확한 사실·동작 불일치는 ‘수정 필요’, 현재 독자에게 생길 오해는 ‘조건/설명 보완’, 문체 선택과 추가 맥락은 ‘선택적 보완’으로 구분한다. 같은 원인의 지적은 묶는다. 판본 전체에 공통인 버전 안내는 한 항목으로 처리한다.

기존 결정을 새 근거로 다시 판단해야 하는 항목은 위 지적들과 구분해 ‘결정 재검토 요청’에 모은다. 단순한 문체 선호나 이미 검토한 근거의 반복은 재검토 사유로 삼지 않는다.

인용은 문제를 식별할 만큼만 짧게 하고, 수정안은 원고에 바로 반영할 수 있게 쓴다. 새 주제나 라이브러리 추가를 해결책으로 강요하지 않는다. 입문 글에 통계 이론 전체를 넣는 대신 판단을 단정한 문장을 좁히는 식으로 고친다.

## 마무리

보고서의 로컬 링크, 코드 펜스·표 문법, 한국어 인코딩과 검토 대상·줄 번호를 확인한다. 보고서만 요청받았다면 원문을 수정하지 않았는지 확인한다. 최종 답변에는 보고서 링크, 핵심 발견, 검증의 중요한 한계만 짧게 전달한다.
