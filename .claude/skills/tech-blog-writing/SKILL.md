# 기술 블로그 글쓰기

신뢰받는 한국 기술 블로그 124편을 분석해 만든 스킬이다(근거: [`docs/references/korean-tech-blog-analysis.md`](../../../docs/references/korean-tech-blog-analysis.md)).
분석에서 신뢰를 가른 것은 문체나 길이가 아니었다. **근거의 밀도**와 **불확실성을 다루는 정직함**이었다.
이 스킬의 모든 단계는 그 두 가지를 지키기 위해 있다.

## 절대 규칙

AI가 쓰는 글에서 가장 위험한 실패는 **그럴듯한 가짜 근거**다. 다음은 어떤 경우에도 지킨다.

1. **실행 출력, 측정값, 버전, 에러 메시지, 이슈 번호를 지어내지 않는다.** 사용자가 준 자료나 이 세션에서 직접 실행한 결과만 쓴다.
2. 근거가 없는 자리는 비우지 말고 표시한다: `<!-- 근거 필요: kubectl get pods 실제 출력 -->`. 초안 단계에서는 본문에 `(미검증)`을 붙인다.
3. 외부 수치(가격, 한도, 벤치마크)를 쓰려면 출처 URL을 붙인다. 가격·한도처럼 버전으로 고정되지 않는 값에는 확인 날짜도 붙인다(P6). 확인할 수 없으면 쓰지 않거나 "확인하지 못함"이라고 적는다.
4. 사용자 자료에 없는 원인 추정은 "추정"이라고 쓴다. 확정처럼 쓰지 않는다.

## 체크포인트 방식

글은 한 번에 쓰지 않는다. 4개의 체크포인트(CP)로 나눠 쓰고, **각 CP에서 멈춰 사용자의 승인을 받은 뒤에만 다음 CP로 넘어간다.**

| CP | 결과물 | 사용자가 검토할 것 |
|---|---|---|
| **CP1 기획** | `00-plan.md` | 유형, 독자, 핵심 메시지, 근거로 쓸 자료와 빈 자료 |
| **CP2 개요** | `01-outline.md` | 섹션 순서, 섹션별 주장, 넣고 뺄 섹션 |
| **CP3 섹션** | `sections/NN-*.md` (2~3개씩) | 설명 깊이, 문체, 예제. 묶음마다 반복한다 |
| **CP4 마무리** | `src/content/blog/<slug>.md` | 제목, description, 전체 검토표 |

### 작업 폴더

초안은 저장소 루트의 `drafts/<slug>/`에 둔다. 이 폴더는 사이트 빌드에 포함되지 않고, `.gitignore`에 들어 있어 커밋되지도 않는다. 초안은 이 PC에만 남으므로 `status.md`의 결정 기록이 유일한 작업 기록이다.

사용자가 준 원자료(노트북, 로그, 설정 파일)는 저장소 루트의 `raw/<주제>/`에 둔다. 이 폴더도 `.gitignore`에 들어 있어 커밋되지 않는다. 원자료 경로는 `status.md`의 "원자료" 줄에 적는다.

```
drafts/<slug>/
├── status.md          # 현재 CP, 결정 기록
├── 00-plan.md         # CP1
├── 01-outline.md      # CP2
└── sections/
    ├── 01-intro.md    # CP3
    ├── 02-....md
    └── ...
```

`status.md`는 세션이 끊겨도 이어서 작업할 수 있게 하는 파일이다. CP를 지날 때마다 갱신한다.

```markdown
# <slug>
- 현재: CP3 (섹션 묶음 2/3 검토 중)
- 원자료: raw/logistic-regression/Logistic_Regression.ipynb

## 결정 기록
- 2026-10-28 CP1 승인: 유형 C, 분야 AI, 반말
- 2026-10-28 CP2 승인: 5절(w 발산)을 핵심으로, sklearn 비교는 6절 유지
```

사용자가 "이어서 써"라고 하면 `drafts/` 아래 `status.md`를 먼저 읽고 거기서 재개한다.

### 체크포인트에서 멈추는 방법

각 CP 끝에서 다음 형식으로 보고하고 **멈춘다.** 같은 응답에서 다음 CP의 작업을 시작하지 않는다.

```markdown
## CP2 개요 검토 요청
결과물: drafts/<slug>/01-outline.md

<결과물 요약: 5~10줄>

판단해 주실 것이 N개 있어서 하나씩 브리핑하고 여쭤볼게요.

### 1/N: <판단할 것의 이름>
<브리핑: 아래 "판단 요청 방식"의 내용>
→ 질문 도구로 질문 하나
```

- 판단 항목은 내가 확신하지 못한 결정, 분량이 크게 갈리는 결정, 근거가 약한 부분을 고른다. "괜찮나요?" 같은 막연한 질문은 쓰지 않는다.
- 승인으로 보는 말: "진행", "좋아", "다음", "승인", "OK" 등. 수정 의견과 승인이 함께 오면 고친 뒤 다음 CP로 간다.
- 수정 의견만 오면 **그 CP의 결과물만** 고치고 다시 검토를 요청한다.
- 뒤 CP에서 받은 의견이 앞 CP의 결정을 바꾸면(예: CP3에서 섹션 순서 변경), 아래 "구조를 바꾸는 피드백"의 절차를 따른다. 해당 파일을 먼저 고치지 않는다.

### 판단 요청 방식

사용자의 판단이 필요하면 **브리핑 → 질문 → 응답 → 다음 항목 브리핑 → 질문 → 응답** 순서로 **한 번에 하나씩** 진행한다. 여러 항목을 목록으로 몰아 묻지 않는다.

1. **브리핑:** 판단에 필요한 정보와 예시를 먼저 보여 준다.
   - 배경: 왜 이 판단이 필요한지, 지금 상태가 어떤지
   - 실제 자료: 바뀌는 문장의 **실제 원문**, 관련 수치, 표의 실제 값. 요약이나 설명으로 대신하지 않는다
   - 선택지마다 무엇이 달라지는지: 넣을 때와 뺄 때의 모습, 분량 변화, 앞뒤 절에 주는 영향
   - 그림이나 구성안이면 ASCII 스케치나 구도 설명
2. **질문:** 질문 도구(AskUserQuestion)로 **질문 하나**만 던진다.
   - 질문 문구는 브리핑을 보지 않아도 무엇을 묻는지 알 수 있게 쓴다.
   - 추천안은 첫 선택지에 두고 "(Recommended)"를 붙인다.
   - 선택지의 미리 보기(preview)에 각 안의 실제 모습(고친 문장, 표, 스케치)을 넣는다.
3. **응답 반영:** 답을 반영하고 `status.md`에 기록한 뒤 다음 항목으로 넘어간다.
4. **"명확히 하고 싶다"는 답이 오면** 내 해석이 어긋났다는 신호로 받는다. 선택지만 바꿔 다시 묻지 말고, 무엇을 더 알고 싶은지 먼저 묻는다. 같은 신호가 두 번 오면 사용자의 요청을 내 말로 다시 정리해 확인받는다(아래 절).

### 구조를 바꾸는 피드백

글의 흐름, 섹션 구성, 편 나누기, 다룰 범위를 바꾸는 피드백을 받으면 **고치기 전에 확인한다.**

1. 요청을 **내 말로 다시 정리**해 보여 준다. 특히 인과 방향(무엇이 출발점이고 무엇이 결론인지)과 무엇을 재료로 쓰라는지를 분명히 적는다.
2. 그 이해를 바탕으로 바뀔 목차나 영향받는 섹션을 표로 보여 준다. 각 항목이 원자료에서 오는지, 새로 만드는 것인지 표시한다.
3. 사용자가 맞다고 확인하고 진행을 지시한 뒤에만 파일을 고친다.
4. 이미 만든 결과물(쓴 섹션, 묶음 계획, 새 그림)에 맞추려고 요청을 줄이거나 미루지 않는다. 요청과 기존 결과물이 부딪치면 결과물을 바꾸는 쪽을 먼저 검토한다.

### 한 번에 쓰기 모드

사용자가 "한 번에 써", "체크포인트 없이", "검토 없이 끝까지"처럼 **명시적으로** 말했을 때만 CP를 건너뛰고 끝까지 쓴다. "써줘", "작성해봐"는 이 모드가 아니다. 이 모드에서도 CP4의 검토표는 보고한다.

## CP1 기획

### 1. 소재 파악

자료에서 알 수 있으면 묻지 않는다.

- 무엇을 겪었거나 만들었거나 읽었는가 (소재)
- 가진 자료: 로그, 명령 출력, 측정 결과, 코드, 설정, 노트북, 링크
- 대상 독자 (입문자 / 실무자 / 특정 스택 사용자). 독자 수준은 근거를 보여 주는 방식을 정한다(CP3 "독자 수준")
- 어미: 반말(~다) 또는 존댓말(~습니다). 분석상 신뢰와 상관이 없으므로 사용자가 고른다. 정하지 않았으면 반말로 제안한다.

### 2. 유형 판별

위에서부터 처음 "예"가 나오는 유형을 **주 유형**으로 정한다. 다른 질문에도 "예"가 있으면 보조 유형으로 적는다(예: T+G).

| 순서 | 질문 | 유형 |
|---|---|---|
| 1 | 실제 장애나 이상 동작을 겪고 원인을 찾았는가? | **T** 트러블슈팅 |
| 2 | 직접 실험하거나 측정해서 질문에 답하는가? | **H** 실습·검증 |
| 3 | 특정 논문, 문서, 릴리스 노트, 책을 읽고 정리하는가? | **R** 리서치·리뷰 |
| 4 | 기술 쟁점에 입장을 펴거나 다른 글에 반론하는가? | **A** 논증·반론 |
| 5 | 독자가 따라 하는 절차를 안내하는가? | **G** 가이드 |
| 6 | 프로젝트, 기간, 경력을 돌아보는가? | **E** 회고·에세이 |
| 7 | 위에 없고, 동작 원리를 설명하는가? | **C** 개념 해설 |

주의할 경계:
- 이상 현상이 계기일 뿐 본문 대부분이 내부 구현 설명이면 T가 아니라 **C**다.
- 장애 없이 동작을 설명하고 오해를 바로잡는 글은 **C**다.
- 측정 없이 장애를 해결한 과정은 H가 아니라 **T**다.

분야도 정한다: **AI**, **BE**, **INF**, 기타(FE, NET, CS). 여러 개일 수 있다.

### 3. 증거 수집

[references/evidence-sheet.md](references/evidence-sheet.md)의 증거 시트를 채운다. 유형과 분야에 필요한 항목만 쓴다.

- 사용자 자료에서 채울 수 있는 칸을 채운다.
- 이 세션에서 직접 실행해 확인할 수 있으면 실행한다(버전 확인, 재현 등). 실행한 명령과 출력을 그대로 기록한다.
- **출력이 이미 있는 자료(노트북, 로그가 붙은 스크립트)는 다시 실행해 원래 출력과 비교한다.** 다르면 그 차이를 기록한다. 셀 실행 순서 문제, 복붙 오류, 오타가 여기서 드러난다.
- 실행 환경은 프로젝트를 오염시키지 않도록 scratchpad의 가상환경 등 격리된 곳에 만든다.
- 원자료의 주장이 의심스러우면(재실행 결과가 다르거나 사실 확인에서 반박된 경우) 확인 실험을 **후보로만** 적는다. 실행 여부는 CP1에서 사용자가 정한다.
- 원자료에 없는 실험, 예제, 그림으로 글을 "보강"하는 후보는 기본적으로 제안하지 않는다. 특히 초급자 대상 개념 글에서는 제안하지 않는다. 사용자가 요청하면 그때 만든다.
- 원자료에 있는 그림, 위젯, 다이어그램을 목록으로만 적지 말고 **열어서 무엇을 설명하는지** 적는다. 이것들은 개요에서 우선 재사용할 재료다.

### CP1 결과물: `00-plan.md`

```markdown
# 기획: <가제>
- 유형: C (H 요소 포함) / 분야: AI / 독자: 머신러닝 입문자 / 어미: 반말
- 핵심 메시지 (한 문장): <독자가 글을 읽고 가져갈 한 가지>
- 원자료: <경로나 링크>

## 증거 시트
<evidence-sheet.md 형식>

## 원자료에서 발견한 문제
- <재실행 결과 원본과 다른 곳, 오타, 버그>

## 추가 확인 실험 후보
- [ ] <실험>: <글에 주는 가치> (예상 소요)

## 비어 있는 필수 자료
- <항목> → 사용자에게 요청
```

**CP1 판단 지점 예:** 유형 판별이 경계에 있는가, 핵심 메시지가 맞는가, 추가 실험 중 무엇을 할 것인가, 빈 자료를 구할 수 있는가.

## CP2 개요

[references/templates.md](references/templates.md)에서 주 유형의 **뼈대**를 가져와 개요를 만든다.

### CP2 결과물: `01-outline.md`

```markdown
# 개요: <가제>

| # | 섹션 제목 | 핵심 주장 (한 줄) | 쓸 증거 | 분량 |
|---|---|---|---|---|
| 1 | 직선으로 0과 1을 맞추면 범위를 벗어난다 | OLS 출력은 [0,1]을 벗어난다 | E1 (OLS 적합 출력) | 짧게 |
| 2 | ... | ... | ... | ... |

## 묶음 계획 (CP3)
- 묶음 1: 섹션 1~2 (도입, 환경)
- 묶음 2: 섹션 3~5
- 묶음 3: 섹션 6~끝 (한계, 정리)

## 뺀 것과 이유
- <후보였지만 뺀 섹션>: <이유>
```

- 섹션마다 증거 ID를 붙인다. **증거가 붙지 않는 섹션은 줄이거나 뺀다.**
- 섹션마다 **출처**(원자료의 어느 부분인지, 새로 만드는 것인지)와 쓸 그림을 적는다. 원자료의 설명 흐름과 그림을 먼저 배치하고, 새로 만드는 것은 따로 표시해 사용자가 넣을지 정하게 한다.
- H, T 유형은 섹션 제목을 **발견 내용의 문장**으로 쓴다. 목차만 읽어도 결론이 보이게 한다.
- 분량은 "짧게 / 보통 / 길게"로 표시해 어디에 무게를 둘지 보이게 한다.
- 제목은 아직 가제다. 최종 제목은 CP4에서 정한다.

**CP2 판단 지점 예:** 어느 섹션이 글의 핵심인가, 순서를 바꿀 곳, 뺄 섹션, 묶음 나누기.

## CP3 섹션 작성

`01-outline.md`의 묶음 계획대로 2~3개 섹션씩 `sections/NN-<이름>.md`에 쓴다. 묶음 하나를 쓰면 멈추고 검토를 받는다.

**사용자 요청이 묶음 순서보다 우선한다.** 사용자가 특정 내용, 그림, 원자료의 일부를 넣으라고 하면 다음 묶음으로 미루지 말고 지금 묶음에서 반영한다. 묶음 계획은 작업 단위일 뿐이고, 요청을 미루는 이유가 되지 않는다. 반영하려면 묶음을 바꿔야 하면 그 사실을 알리고 바꾼다.

### 작성 원칙

| # | 원칙 |
|---|---|
| P1 | **실제로 해 본 증거를 보인다.** 명령 뒤에 실제 출력, 수정 뒤에 같은 조작으로 재검증, 측정에는 대조군. 증거를 본문·각주·첨부 노트북 중 어디에 둘지는 독자 수준을 따른다(아래 "독자 수준"). |
| P2 | **확정, 추정, 미확인을 문장 단위로 구분한다.** "확인했다" / "~로 보인다" / "확인하지 못했다". |
| P3 | **공통 실행 환경과 버전을 프런트매터 `env` 한 곳에 모은다.** 레이아웃이 제목 아래 버전 꼬리표로 보여 주므로 본문에는 다시 쓰지 않는다. 날짜는 쓰지 않는다. 시점은 버전과 `pubDate`로 충분하다. 결과를 해석하거나 재현하는 데 필요한 실험별 조건(반복 횟수, 데이터 크기, 설정)은 환경 정보가 아니므로 독자 수준에 따라 본문·각주·첨부 노트북에 적는다. |
| P4 | **틀린 가설과 헛걸음을 지우지 않는다.** 왜 틀렸는지 한 줄을 붙인다. |
| P5 | **한계와 적용 범위를 밝힌다.** "재지 않은 것", "이럴 땐 쓰지 마라". |
| P6 | **수치에 출처와 조건을 붙인다.** 직접 잰 값, 인용한 값, 환산한 값을 구분한다. 확인 날짜는 가격·한도처럼 버전으로 고정되지 않고 시간에 따라 바뀌는 값에만 붙인다. |
| P7 | **남의 주장과 내 해석을 문장으로 나눈다.** "저자들은 ~라고 한다" / "내 해석으로는". |
| P8 | **핵심 근거는 텍스트로 남긴다.** 로그, 출력, 설정을 이미지로만 두지 않는다. |
| P9 | **제목과 결론이 본문 근거보다 강하지 않게 한다.** |
| P10 | **글 끝에 작성 노트나 AI 고지를 두지 않는다**. 확인하지 못한 주장은 본문의 그 자리에 표시한다(P2). |

문체:
- 도입은 3문단 안에 구체적인 증상, 사실, 예제 결과로 들어간다. "~를 운영하다 보면" 같은 일반론으로 시작하지 않는다. "이런 질문이 남는다", "왜 ~할까?"처럼 독자에게 질문을 던지는 틀도 과하므로 쓰지 않는다.
- 분량은 개요의 표시를 따른다. 사소한 단계는 한두 줄로 줄이고 핵심 원인과 근거에 쓴다.
- 감정 서술은 짧게 한다. 반복하면 근거를 희석한다.
- 비유를 쓰면 그 비유가 깨지는 지점도 쓴다. 단 G 유형(가이드, 레시피형)에서는 비유를 규칙 문장 안에 한 줄로 녹이고, "비유가 깨지는 지점" 같은 소제목을 만들지 않는다.

**자료 언급 금지(완결성):**
- 사용자가 준 원자료(`raw/`의 노트북, 학습지, 교재, 수업 자료)는 글 어디에서도 언급하지 않는다. 글은 **본문과 첨부 파일(예: 내려받기 노트북)만으로 완결**되어야 한다.
- 원자료는 다룰 내용을 고르고 근거를 얻는 데 쓴다. 출력은 원자료가 아니라 글에 첨부하는 자료(새로 쓴 노트북 등)에서 가져온다.
- "노트북에서 ~해 봤다", "출력을 보면"처럼 실행 경위를 서술하지 않는다. 규칙을 먼저 쓰고 예제는 그 규칙을 확인하는 자리에 둔다.

**원자료 재사용:** "언급하지 않는다"는 "쓰지 않는다"가 아니다.
- 원자료의 **설명 흐름, 그림, 다이어그램, 인터랙티브 위젯**은 우선 재사용한다. 출처를 밝히지 않고 글의 일부로 옮긴다(위젯은 컴포넌트로 이식하고, 수치는 첨부 노트북으로 다시 계산해 맞춘다).
- 원자료에 없는 그림, 예제, 실험, 섹션을 새로 만들어 원자료보다 앞세우지 않는다. 새로 만들려면 먼저 무엇을 왜 만드는지 브리핑하고 사용자 승인을 받는다.
- 원자료의 내용 중 사실 확인에서 틀린 것은 고쳐 쓰되, 흐름은 유지한다.

**주제 집중:** 예제와 설명은 글의 주제(예: NumPy 사용법) 안에서 끝낸다. 다른 분야의 개념(예: 시그모이드, softmax, 손실 함수, 모델, 배치, 학습·검증 분할)을 예제나 쓰임새 설명으로 끌어오지 않는다. 독자의 집중을 흩뜨린다. 쓰임새를 보여 줘야 하면 주제와 같은 수준의 중립적인 예(점수표, 이미지 배열 같은 데이터 모양)를 쓴다. 예제 수도 규칙 하나에 하나를 기본으로 한다.

**분량:** 한 편이 길어 스크롤이 길면 가독성이 나쁘다. 다만 분량은 **참고값**이고, 글의 흐름보다 앞서지 않는다.
- 바이트 수로 재지 않는다. 한글은 글자당 3바이트라 같은 글도 영문보다 세 배 길게 잡힌다. **본문 글자 수**(공백 포함, 코드 블록·표·그림·컴포넌트 제외)로 잰다.
- 기준: 편당 약 3,000~4,000자. 약 5,000자를 넘으면 검토한다. 그림·위젯이 많은 개념 글은 그림이 쉼표 역할을 하므로 조금 넘어도 괜찮다.
- 넘으면 먼저 **줄이기**(중복된 요약, 주제 밖 예시, 다른 편과 겹치는 내용)를 제안한다. **나누기**는 한 편의 논리 흐름이 끊기지 않을 때만 제안한다. 논리가 하나로 이어진 글(문제 → 해결 → 구조처럼)을 분량 때문에 가르지 않는다.

**독자 수준:** CP1에서 정한 독자에 맞춰 근거를 보여 주는 방식을 고른다. 근거를 빼는 것이 아니라 놓는 자리를 바꾸는 것이다.
- **초급자 대상 개념 글:** 본문은 설명 흐름과 그림 중심으로 쓴다. 수치는 결과만 쓰고, 실행 조건·엄밀한 정리 조건·학습 설정은 각주로, 계산 과정은 첨부 노트북으로 보낸다. 용어는 처음 나올 때 한 번 풀어 쓴다. 코드 블록과 출력 블록은 꼭 필요할 때만 둔다.
- **실무자 대상, 실습·트러블슈팅 글:** 지금까지처럼 명령, 실제 출력, 측정 조건을 본문에 둔다(P1, P8).

### 렌더링 확인

쓰기 전에 사이트가 지원하는 문법을 확인한다(`astro.config.*`, `package.json`).

- 수식(`$$`), Mermaid 같은 다이어그램은 플러그인이 없으면 글자 그대로 보인다. 지원하지 않으면 ` ```txt ` 블록("식" 상자)으로 쓴다.
- **코드 실행 결과는 ` ```output `으로 쓴다.** 코드 블록 머리 줄에 "출력" 라벨이 붙는다. ` ```txt `는 식·도식·손으로 따라간 계산에만 쓴다. 본문에 코드 없이 결과만 보이는 경우(노트북 셀의 출력)도 ` ```output `이다.
- **인용문은 상자로 그려진다.** 첫 줄로 종류가 정해진다: `> **용어:** …`(용어 설명), `> **체크:** …`(독자에게 권하는 점검), `> ⚠ …`(주의), `> **굵은 핵심 문장.** …`(핵심 문장). 머리말(`**용어:**`, `⚠`)은 상자 라벨이 대신하므로 화면에는 나오지 않는다. 이 넷에 맞지 않는 인용문은 회색 세로줄로 남는다.
- **표 안의 `|`는 `\|`로 쓴다.** 인라인 코드 안이라도 표의 칸 구분자로 해석되어 칸이 밀리고 내용이 사라진다(이 사이트에서 빌드해 확인했다). 일반 문단과 코드 블록의 `|`는 그대로 둔다.
- 플러그인 추가는 사이트 설정 변경이므로 사용자에게 제안만 한다.
- **그림과 위젯은 빌드한 화면으로 확인한다.** 데스크톱과 휴대폰 폭(약 390px)에서 스크린샷을 찍는다. 단계가 있는 위젯은 첫 화면만이 아니라 중간과 마지막 단계도 본다. 글자 넘침, 겹침, 글꼴에 따라 깨지는 기호(유니코드 빼기 − 등)를 찾는다.

### 묶음마다 하는 자체 점검

검토를 요청하기 전에 그 묶음에 대해 확인한다.

- 주 유형 체크리스트 중 이 섹션에 해당하는 항목
- 출력과 수치의 근거를 증거 시트와 첨부 노트북·`verify/` 실행 기록에서 찾는다. 근거가 있는데 시트에만 빠졌으면 그 위치를 시트에 채운다. 어디에도 없으면 실행해서 확인하고, 확인할 수 없으면 `<!-- 근거 필요 -->`로 표시한다. 실행하지 않은 값을 실제 결과처럼 썼다면 안티패턴 AP15(지어낸 근거)다([근거 판정](../../../docs/writing/anti-patterns.md))
- [한국어 정오표](../../../docs/writing/korean-errata.md)에 등록된 유형이 있는가. 정오표의 "적용 원칙"을 따른다. "고치지 않은 것" 표의 결정은 적용 범위 안에서 같은 문맥과 같은 근거로 다시 지적하지 않는다. 문맥이 달라졌거나 새 근거가 있으면 기존 결정과 달라진 조건을 밝히고 재검토를 요청한다
- 개요의 핵심 주장과 실제로 쓴 내용이 같은가. 달라졌으면 보고한다.

### CP3 검토 요청 형식

```markdown
## CP3 섹션 검토 요청 (묶음 2/3)
결과물: drafts/<slug>/sections/03-*.md ~ 05-*.md

- 03 <제목>: <한 줄 요약>
- 04 <제목>: <한 줄 요약>

**개요와 달라진 점:** <없으면 "없음">

<판단 항목이 있으면 "판단 요청 방식"대로 하나씩 브리핑 → 질문>

승인하시면 묶음 3(섹션 6~8)을 씁니다.
```

이미 승인한 섹션을 고칠 때는 그 파일만 고치고, 다른 섹션의 표현을 맞춰야 하면 목록으로 알린다.

## CP4 마무리

모든 섹션이 승인되면 다음을 한다.

1. **제목, description, 카테고리, 대표 이미지를 정한다.** 대표 이미지(`heroImage`, 2:1)는 홈·목록 카드와 공유 미리보기(og:image)에 쓰인다. 글 화면에는 나오지 않는다. 만든다면 본문에 실린 데이터로만 그린다. 본문이 나온 뒤에 정해야 본문보다 강하지 않게 쓸 수 있다(P9). 후보 2~3개를 제시한다.
   - **description은 글 화면에도 나온다.** 제목 바로 아래 소개 문단(lead), 목록 카드 요약, 검색·공유 미리보기에 같은 문자열이 쓰인다. 문자열 하나라 목록을 넣을 수 없으므로, 기능이나 항목을 늘어놓지 말고 주제를 한 문장으로 쓴다([정오표](../../../docs/writing/korean-errata.md) K18). 항목 목록은 본문의 "한눈에 보기" 표 같은 자리가 맡는다.
2. **글 끝에 작성 노트나 AI 고지를 두지 않는다.** 사용자가 따로 요청할 때만 넣는다([references/evidence-sheet.md](references/evidence-sheet.md#작성-노트)).
3. **섹션을 합쳐 `src/content/blog/<slug>.md`를 만든다.** 프런트매터 스키마(`src/content.config.ts`):

   ```yaml
   ---
   title: '제목'
   description: '한 문장 요약'
   category: 'AI/머신러닝'   # 필수. '/'로 단계를 나눈다. 기존 글의 카테고리를 먼저 확인하고 사용자에게 묻는다
   pubDate: 'YYYY-MM-DD'
   updatedDate: 'YYYY-MM-DD'   # 갱신할 때만
   heroImage: '../../assets/파일명.jpg'   # 선택
   series: mlp            # 시리즈 글이면 src/content/series/<id>.yaml의 id
   seriesOrder: 2         # 시리즈 글이면 편 번호(1부터). series와 함께 쓴다
   env: ['Python 3.14.8', 'NumPy 2.5.4']   # 실행 환경 버전. 코드가 없는 글은 뺀다
   notebook: true         # public/notebooks/<slug>.ipynb가 있으면 true(내려받기 카드)
   ---
   ```

   - **본문에 쓰지 않는 것:** 시리즈 안내 인용문(`> **… 시리즈:** …`), 실행 환경 줄(`> **실행 환경:** …`), 노트북 내려받기 링크. 레이아웃이 프런트매터에서 시리즈 메뉴·버전 꼬리표·노트북 카드를 만든다. 그 글에만 해당하는 안내("이 글은 개념만 다루고 코드는 2편에서 다룬다")는 본문 평문으로 쓴다.
   - **시리즈:** 새 시리즈는 `src/content/series/<id>.yaml`에 `title`과 `parts`(편 제목 목록, 아직 안 쓴 편 포함)를 만든다. 새 편을 쓰면 그 글의 `seriesOrder`만 맞추면 되고 이전 글은 고치지 않는다. 편 제목이 바뀌면 YAML을 고친다.

   slug는 영문 소문자와 하이픈으로 만든다.

   **만든 파일은 그 자리에서 `status.md`에 적는다.** 글, 노트북 복사본, 시리즈 YAML, 대표 이미지처럼 사이트에 들어가는 파일을 만들면 CP4가 끝나기 전이라도 바로 기록한다. 세션이 끊긴 뒤 무엇이 반영됐는지 파일을 하나씩 열어 대조하지 않아도 되게 하려는 것이다.
4. **빌드를 확인한다.** `npx astro build`가 통과하는지 본다.
5. **전체 검토를 한다.** 다음 네 가지를 차례로 점검한다.
   1. 주 유형의 **필수 체크리스트** ([references/templates.md](references/templates.md))
   2. 분야 **근거 체크리스트** ([references/domains.md](references/domains.md))
   3. **안티패턴** ([docs/writing/anti-patterns.md](../../../docs/writing/anti-patterns.md))
   4. **한국어 정오표** ([docs/writing/korean-errata.md](../../../docs/writing/korean-errata.md)). 한국어 검토에서 새로 지적되어 고친 표현과 리뷰 보고서의 새 유형 후보는 writing-rules-update 스킬로 정오표·안티패턴에 반영한다

   여러 편이나 긴 글이라 이 점검을 하위 에이전트에 맡길 때는 브리프에 다음을 넣는다. 에이전트는 브리프에 없는 기록을 모르므로, 빠지면 이미 확인한 주장을 "근거 없음"으로 들거나 사용자가 정한 문장을 다시 지적한다.
   - 실행 확인 기록의 위치: 노트북 출력뿐 아니라 `verify/`의 확인 스크립트와 출력 파일
   - 사용자가 이미 결정하거나 승인한 사항(`status.md` 결정 기록)과 정오표의 "고치지 않은 것": 같은 문맥과 같은 근거로는 다시 지적하지 않을 것. 문맥이 달라졌거나 새 근거가 있으면 기존 결정과 달라진 조건을 밝혀 따로 보고할 것
   - 돌아온 지적은 인용한 줄을 파일에서 다시 확인하고 실행 기록과 대조한 뒤 보고한다. 에이전트의 수정안도 그대로 넣지 말고 안티패턴 AP18로 점검한다

### CP4 검토 요청 형식

```markdown
## CP4 마무리 검토 요청
결과물: src/content/blog/<slug>.md (빌드 통과)

**검토표**
| 항목 | 상태 | 위치 | 조치 |
|---|---|---|---|
| <통과 항목 묶음> | 통과 | | |
| 수정 후 같은 조작으로 재검증 | 미통과 | §5 | 재배포 후 같은 요청을 보낸 출력 필요 |

남은 `<!-- 근거 필요 -->`: N개

<판단 항목(검토에서 나온 수정, 제목·description, 게시일, 대표 이미지)을 "판단 요청 방식"대로 하나씩 브리핑 → 질문.
제목은 목록 카드·시리즈 줄에서 보일 모습을 미리 보기에 넣고, 대표 이미지는 구도 스케치를 넣는다>
```

승인 후:
- `status.md`를 "완료"로 갱신한다. `drafts/<slug>/`는 지우지 않는다. 지울지는 사용자가 정한다.
- 갱신하는 글이면 `updatedDate`를 바꾸고 본문 끝에 변경 이력을 남긴다.
- 커밋은 사용자가 요청할 때만 한다.

## 기존 글 검토 모드

사용자가 이미 쓴 글의 검토를 요청하면 CP를 쓰지 않는다.

1. 글의 유형과 분야를 판별해 알린다.
2. CP4의 네 가지 점검을 한다.
3. 출력·수치의 근거는 [안티패턴](../../../docs/writing/anti-patterns.md)의 '근거 판정'에 따라 구분한다. 첨부 노트북이 있으면 실행해 확인할 수 있다(원고는 고치지 않는다). 확인되지 않으면 '근거 확인 필요'로, 실행하지 않은 값을 실제 결과처럼 쓴 사실이 확인되면 AP15로 보고한다. 출처 표기가 없는 수치는 AP2로 따로 적는다. 핵심 주장에 영향을 주는 항목은 맨 위에 적되 이 상태들을 구분한다.
4. 사용자가 고쳐 달라고 할 때만 고친다. 고칠 때도 새 근거를 지어내지 않고 `<!-- 근거 필요 -->` 표시를 넣는다.
5. 크게 다시 쓰는 경우(구조 변경)라면 기존 글을 `drafts/<slug>/`로 나눠 CP2부터 진행하자고 제안한다.
