# 유형별 템플릿

## T 트러블슈팅

**뼈대**
1. **증상:** 로그 한 줄, 알림 문구, 수치 대조, 모순된 관측 중 하나로 시작한다. 맥락은 3문단 안에 끝낸다.
2. **환경과 범위:** 버전은 프런트매터 `env`에 넣고(P3), 본문에는 재현 범위와 문제에 관련된 설정만 쓴다. 사내 코드라면 일반화 고지("이름은 바꿨다")를 둔다.
3. **조사 경로:** 가설 → 검증 → 기각을 반복하거나, 위 계층에서 아래 계층으로 내려간다.
4. **근본 원인과 기전:** 다이어그램이나 타임라인으로 "왜 그렇게 되는가"를 보인다.
5. **수정:** 임시 조치와 근본 조치를 나누고, 버린 대안과 그 이유를 적는다.
6. **검증:** 문제를 일으킨 것과 같은 조작으로 다시 시험하고 전후 수치를 비교한다.
7. **재발 방지:** 알림, IaC, 테스트, 남은 과제. 교훈은 원칙 문장 1~3개로 줄인다.

**변형**
- 결론 선행형: 원인을 앞에 밝히고 본문을 그 증명으로 쓴다. 원인이 의외일 때 좋다.
- 추리형: 가설 하나하나를 헤딩으로 세운다. 가설이 3개 이상일 때 좋다.
- 계층 하강형: 애플리케이션 → 런타임 → 커널 → 네트워크 순으로 내려간다.
- 미해결 메모형: 해결하지 못했으면 "미해결"을 제목이나 첫 문단에 밝히고, 확인한 것과 남은 가설을 적는다.

**필수 체크리스트**
- [ ] 도입 3문단 안에 구체적인 증상이 있다. 일반론 서론이 없다.
- [ ] 틀렸던 가설과 그것을 기각한 근거가 남아 있다.
- [ ] 원인을 문서 인용만이 아니라 재현이나 단일 변수 실험으로 증명했다. 못 했으면 "추정"으로 적었다.
- [ ] 수정을 같은 조작으로 재검증했다. 남은 나쁜 수치도 숨기지 않았다.
- [ ] 관련 업스트림 이슈나 PR 번호, 수정이 포함된 버전을 적었다(있을 때).
- [ ] 분량을 깊이에 비례해 배분했다.

## H 실습·검증

**뼈대**
1. **계기와 질문:** 계기를 밝히고 "~인가?" 형태의 질문으로 좁힌다. 예상(가설)도 적는다.
2. **결과 미리 보기 (선택):** 요약표 하나.
3. **최소한의 개념:** 실험을 이해하는 데 필요한 것만.
4. **환경과 설계:** 바꾼 변수, 고정한 변수, 대조군, 측정 절차. 버전은 프런트매터 `env`에 넣는다(P3).
5. **실험 블록 반복:** 조건 → 코드 → 원시 출력 → 표 → 해석을 한 단위로 반복한다.
6. **원인 분석:** 프로파일러, 트레이스, 설정 덤프로 "왜"를 설명한다.
7. **한계와 하지 않은 것**
8. **정리:** 요약표나 권장 사항, 다른 환경에 가져갈 판단 규칙, 재현 저장소 링크.

**필수 체크리스트**
- [ ] 바꾼 변수 하나 외에는 똑같은 대조군이나 기준선이 있다.
- [ ] 반복 횟수, 워밍업, 대표값(중앙값 등)과 분산을 적었다.
- [ ] 측정하기 전에 측정하려는 현상이 실제로 일어났는지 먼저 보였다.
- [ ] 예상과 다른 결과와 자기 측정 오류를 숨기지 않았다.
- [ ] "재지 않은 것"을 밝혀 일반화 범위를 제한했다.
- [ ] 측정값과 인용값을 구분했다.
- [ ] 섹션 제목이 발견 내용의 문장이다.

## C 개념 해설

**뼈대**
1. **독자의 의문:** 독자가 겪을 증상, 에러, 의문으로 시작하고 답할 범위를 예고한다.
2. **정의와 최소 재현:** 한 문장 정의 뒤에 가장 작은 실행 예제.
3. **존재 이유:** 이전 방식의 한계 → 새 방식이 필요한 이유(진화 서사).
4. **메커니즘:** 한 축(시간, 호출, 진화 순서 중 하나)을 정해 끝까지 지킨다.
5. **함정과 오해 교정**
6. **실무 판단 기준:** 써야 하는가, 쓰면 안 되는 조건, 대안 비교.
7. **마무리:** 요약, 독자가 가져갈 진단 질문이나 규칙, 참고 자료.

**필수 체크리스트**
- [ ] 흔한 오해를 하나 이상 명시적으로 바로잡았다.
- [ ] 글 전체를 관통하는 예제 하나를 반복해 썼다.
- [ ] 비유나 단순화를 쓴 뒤 그것이 깨지는 지점을 밝혔다. (C 주 유형에만 적용. G 보조로 쓸 때는 적용하지 않는다)
- [ ] 분야 관습에 맞는 1차 근거(명세, 소스 코드, 공식 문서)를 달았다.
- [ ] 확실하지 않은 부분을 그 자리에서 표시했다.
- [ ] 알려진 반론이나 트레이드오프를 다뤘다.

## G 가이드

**뼈대**
1. **문제와 동기**
2. **범위와 기준 환경:** 대상 독자, 목표. 도구 버전과 OS는 프런트매터 `env`에 넣는다(P3).
3. **개념 한 컷:** 표나 다이어그램 하나로 전체 그림.
4. **가장 짧은 성공 경로:** 스모크 테스트와 성공 판정 기준을 먼저.
5. **기능별 단계:** 명령 → 실제 출력 → 설명을 반복한다.
6. **주의, 함정, 언제 쓰지 말까:** 실제로 겪은 에러 원문과 회복 방법.
7. **마무리:** 요약, 다음 첫 행동, 정리(cleanup) 명령, 참고 링크.

**변형**
- 위키형: 서론 없이 created/updated 날짜를 쓴다. 낡은 내용은 Deprecated 섹션으로 옮긴다.
- 런북형: 장애 대응 순서. 판단 분기마다 확인 명령과 기대 출력을 둔다.
- 레시피 모음형(사용법 참고 문서): 기준 버전을 맨 앞에 한 번 적는다. 형식은 다음과 같다.
  - 글 맨 앞: 본문은 **"한눈에 보기" 표**(하고 싶은 것 / 코드 / 결과·주의, 행마다 해당 절 링크)로 바로 시작한다. 글 소개는 프런트매터 `description`이 맡는다. 레이아웃이 제목 바로 아래 소개 문단으로 보여 주고, 목록 카드와 검색 미리보기에도 쓰인다. 표와 같은 항목을 표 앞에 문장이나 목록으로 다시 쓰면 소개 문단 → 첫 문단 → 표로 같은 내용이 세 번 나오므로 쓰지 않는다. 그 글에만 해당하는 안내(시리즈 마지막 편의 "끝에 다섯 편의 핵심을 표로 모았다" 등)만 표 앞 한 문장으로 둔다. 버전과 첨부 노트북은 본문에 쓰지 않고 프런트매터 `env`·`notebook`에 적는다(레이아웃이 버전 꼬리표와 노트북 카드를 만든다).
  - 출력: 코드 뒤 실제 출력은 ` ```output ` 블록으로 쓴다.
  - 각 항목: 소제목은 **작업 이름**("열 하나 꺼내기", "축 추가"). 규칙 한두 줄 → 최소 예제(코드와 실제 출력) → `⚠ 주의` 한 줄과 대책.
  - 측정·벤치마크처럼 코드가 긴 항목은 본문에 방법과 결과 표만 두고, 코드는 첨부 노트북의 셀 이름으로 가리킨다.
  - 시리즈의 마지막 편에는 편별 핵심 한 줄씩을 모은 "시리즈 정리" 표를 둔다.
  - 쓰지 않는 것: 실험 보고형 서술, 일화로 시작하는 도입, "주의할 점 N" 같은 번호 소제목, C 유형의 "비유가 깨지는 지점" 소제목.
- 체험형: 새 도구를 직접 써 본 기록. 실제 출력과 공식 문서와 다른 점이 핵심이다.

**필수 체크리스트**
- [ ] 모든 핵심 명령 뒤에 실제 출력이 텍스트로 있다.
- [ ] 바뀔 수 있는 수치에 출처가 있다. 기본값은 버전으로, 가격·한도처럼 버전으로 고정되지 않는 값은 확인 날짜로 시점을 밝힌다.
- [ ] 버전을 고정했다. `latest` 태그나 버전 없는 설치 명령이 없다.
- [ ] 공식 문서와 실제 동작이 다른 지점을 표시했다.
- [ ] 갱신하는 글이면 Updated 날짜와 변경 이력이 있다.

## R 리서치·리뷰

**뼈대**
1. **원문 식별:** 제목, 저자나 기관, 연도, 링크를 맨 앞에.
2. **동기와 선별 범위:** 왜 읽었고 어디까지 다루는가.
3. **원문의 한계를 먼저:** 표본, 재현 가능성, 빠진 실험을 요약보다 앞에.
4. **배경 개념**
5. **본문:** 원문 구조를 따르거나 필자가 고른 발견 순서로.
6. **필자 해석:** 별도 섹션이나 문장 표지로 원문과 분리한다.
7. **마무리:** 교훈과 원문 읽기 권유.

**필수 체크리스트**
- [ ] 원문 주장과 내 해석을 술어("~라고 보고한다" / "내 생각에는")나 헤딩으로 구분했다.
- [ ] 하위 그룹이나 작은 표본의 결과를 전체로 일반화하지 않았다. 제목이 본문보다 강하지 않다.
- [ ] 옮긴 수치마다 출처와 측정 조건을 적고, 집계 방식이 바뀌었는지 확인했다.
- [ ] 원문이 스스로 밝힌 약점을 그대로 전했다.
- [ ] AI 요약이나 번역을 썼다면 인용한 문장과 수치를 원문과 대조했다.

## E 회고·에세이

**뼈대**
1. **사실 앵커:** 기간, 규모, 수치로 시작한다.
2. **쓰는 이유와 해당 독자**
3. **필자의 맥락:** 역할, 팀 규모, 조건.
4. **본문:** 시간순, 주제별, 질문별 중 하나로.
5. **실패와 어려움**
6. **교훈**
7. **다음 계획이나 열린 질문**

**필수 체크리스트**
- [ ] 필자의 맥락을 밝혀 독자가 일반화 범위를 스스로 판단할 수 있다.
- [ ] 주장의 적용 대상을 글 앞에 적었다.
- [ ] 주요 결정을 "평소 원칙 → 이번 선택과 그 조건 → 치른 비용" 3단으로 기록했다.
- [ ] 성과 수치에 측정 방식이 있다. 자기 보고 수치는 자기 보고라고 밝혔다.
- [ ] 실패나 미완료를 한 곳 이상 기록했다.
- [ ] 홍보가 마무리를 덮지 않는다.

## A 논증·반론

**뼈대**
1. **상대 주장 요약:** 반론이면 상대 주장을 공정하게, 링크와 함께.
2. **공통 기반:** 양쪽이 동의하는 사실과 공식 동작.
3. **반대 측의 가장 강한 근거를 인정한다.**
4. **쟁점 재정의:** 쟁점을 한 단계 위로 끌어올린다.
5. **사례별 검증:** 반례 코드나 실험, 빈도, 비용, 대안.
6. **조건부 결론:** 결론이 성립하는 조건을 좁히고 가치 전제를 밝힌다.
7. **마무리:** 부분 동의와 권고.

**필수 체크리스트**
- [ ] 상대의 가장 강한 근거를 먼저 인정했다.
- [ ] 반례를 실행 가능한 코드나 데이터로 제시했다.
- [ ] 결론을 조건부로 좁히고, 기술 우열이 아니라 가치나 팀 운영 판단임을 밝혔다(해당할 때).
- [ ] 외부 연구를 인용했다면 연구의 결론과 내 해석을 분리했다.
- [ ] 상대를 인신공격하지 않고 주장만 다뤘다.

## 혼합 유형

주 유형의 뼈대를 따르고, 보조 유형의 체크리스트를 해당 구간에만 적용한다.

| 조합 | 구성 |
|---|---|
| T+G | 앞부분은 T(시도와 원인), 뒷부분은 G(최종 구성 절차). 경계에 "여기부터는 최종 설정"이라고 적는다. |
| C(T 도입) | 이상 현상 한 문단으로 시작하고 바로 C 뼈대로 넘어간다. 원인 증명 대신 메커니즘 설명에 분량을 쓴다. |
| H+E | 측정 결과에서 판단 기준을 끌어낸다. 측정 구간은 H 체크리스트, 판단 구간은 E의 맥락 밝히기를 적용한다. |
| C+E | 해설 뒤에 필자 입장으로 끝난다. 입장 부분은 "내 생각"으로 명시한다. |
| AI × T | 샘플이 적어(2편) 별도 템플릿이 없다. T 뼈대에 [domains.md](domains.md)의 AI 체크리스트를 전부 적용한다. |
