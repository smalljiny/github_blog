# 안티패턴

글쓰기 스킬(tech-blog-writing)의 CP3 자체 점검과 CP4 검토, 리뷰 스킬(review-technical-draft)의 원고 리뷰에서 하나씩 확인한다. 발견하면 위치와 고치는 방법을 보고한다.
반례 샘플 번호는 [`docs/references/korean-tech-blog-analysis.md`](../references/korean-tech-blog-analysis.md) §5에 있다.

- '찾는 방법'은 점검할 후보를 찾는 단서다. 글의 유형과 독자 수준에 비추어 실제 문제인지 판단한 뒤 지적한다.
- 같은 원인의 문제는 대표 항목 하나로 한 번 보고하고, 관련 번호를 함께 적는다(예: "AP15, AP9 관련").
- 리뷰에서 기존 유형에 맞지 않는 문제를 찾으면 보고서의 "안티패턴 새 유형 후보"에 남긴다. 원고를 고친 Claude 쪽에서 writing-rules-update 스킬로 검증한 뒤 반영한다. 새 번호는 뒤에 붙이고 지운 번호는 다시 쓰지 않는다. 합치거나 없앨 때는 기존 번호 행에 대체 안내를 남긴다.

| # | 안티패턴 | 찾는 방법 | 고치는 방법 |
|---|---|---|---|
| AP1 | 버전과 환경 없는 벤치마크나 트러블슈팅 | 측정·재현 결과를 해석하는 데 필요한 환경 조건(버전, 하드웨어, 설정)이 없다. 레시피의 기준 버전 표기는 AP14가 맡는다 | 공통 환경과 버전은 프런트매터 `env`에 넣고, 결과에 영향을 준 실험·재현 조건(반복 횟수, 데이터 크기, 설정)은 독자 수준에 따라 본문·각주·첨부 노트북에 적는다(P3) |
| AP2 | 출처, 추정 여부 없는 수치 | 숫자마다 "어디서 왔나"를 묻는다 | 출처를 붙이거나(시간에 따라 바뀌는 값은 확인 날짜도), 추정이라고 쓰거나, 뺀다 |
| AP3 | 실행하지 않은 튜토리얼 | 실행 결과를 주장하지만 본문·첨부 노트북·실행 기록 어디에서도 그 결과를 확인할 수 없다. 본문에 출력이 없다는 것만으로는 해당하지 않는다(초급자 글은 출력을 각주나 첨부 노트북에 둘 수 있다) | 실제 실행 결과를 본문에 넣거나 첨부 자료로 연결한다. 확인할 수 없으면 `<!-- 근거 필요 -->` |
| AP4 | 해결안을 제안만 하고 적용 결과가 없음 | "~하면 된다"로 끝나고 적용 후 관측이 없다 | 적용 결과를 넣거나 "적용 전"이라고 밝힌다 |
| AP5 | 원인을 "조사 결과"로만 제시 | 원인 절에 문서 인용만 있고 재현이 없다 | 재현이나 단일 변수 실험을 넣거나 "추정"으로 바꾼다 |
| AP6 | 핵심 근거를 이미지로만 제시 | 로그, 출력, 설정이 스크린샷뿐이다 | 텍스트 코드 블록을 함께 둔다 |
| AP7 | 제목이 본문 근거보다 강함 | 제목과 description의 주장이 본문의 조건과 표본 범위를 넘는다 | 조건을 제목에 넣거나 주장을 약하게 한다 |
| AP8 | 측정 방식 없는 성과 수치 | "N% 개선"에 기준선과 측정법이 없다 | 측정법과 기준선을 쓴다. 없으면 정확한 수치를 빼고 관찰한 내용으로 쓴다. 자기 보고 수치를 인용할 때는 출처와 측정의 한계를 밝힌다 |
| AP9 | AI 생성 내용을 검증 없이 게시 | 확인하지 못한 주장이 본문에서 확정처럼 쓰였다. 출력·수치를 만들어 근거처럼 제시한 경우는 AP15가 맡는다 | 확인하지 않은 주장은 그 자리에 표시하거나 확인된 범위로 좁힌다 |
| AP10 | 알려진 반론 누락, 결론 없이 끝남 | 선택·추천·논증이 있는 글에서 판단에 영향을 주는 단점이나 대안을 다루지 않았다. 이와 별개로, 마지막 절이 글의 목적(요약, 판단, 다음 단계)에 맞게 끝나는지 본다 | 관련 한계와 대안을 해당 자리에 적고, 판단을 담은 글은 조건부 결론으로 마무리한다. 트레이드오프 절은 필요할 때만 두고, 사용법 글에 일괄 요구하지 않는다 |
| AP11 | 일반론 서론 | 첫 문단이 "~를 운영하다 보면", "요즘 ~가 화제다" | 구체적인 증상, 사실, 예제 결과로 시작한다. 독자에게 질문을 던지는 틀("왜 ~할까?")로 바꾸지 않는다 |
| AP12 | 코드 식별자 오탈자, 복붙 오류 | 본문의 함수명·변수명·명령이 코드 블록과 다르다 | 의도, 기준 버전, 실행 결과와 대조해 틀린 쪽을 고친다. 코드가 틀렸으면 코드와 출력, 설명을 함께 고친다. 단순 오탈자는 확인된 이름으로 맞춘다 |
| AP13 | `latest` 태그, 버전 없는 설치 명령 | `:latest`, `pip install foo`, `npm i foo` | 버전을 고정한다 |
| AP14 | 기준 버전 없는 레시피 | 프런트매터에 `env`가 없다. 또는 본문에 "실행 환경" 줄을 따로 썼다. 벤치마크·트러블슈팅의 환경 조건은 AP1이 맡는다 | 버전을 프런트매터 `env`에 넣고, 본문의 실행 환경 줄이 `env`와 겹치면 지운다. 실험·재현 조건은 지우지 않는다. 날짜는 넣지 않는다 |
| AP15 | 지어낸 근거 (AI 특유) | 실행하지 않은 출력, 수치, 이슈 번호를 실제 근거처럼 제시했다. 이용 가능한 자료에서 찾지 못했다는 것만으로는 확정하지 않는다(아래 "근거 판정") | 만든 사실이 확인되면 지우거나 실제 실행 결과로 바꾼다. 확인 중이면 `<!-- 근거 필요 -->` |
| AP16 | 확신 과잉 어휘 | "반드시", "항상", "완벽하게", "모든"이 근거 없이 쓰였다 | 조건을 붙이거나 약한 표현으로 바꾼다 |
| AP17 | 이 글의 선택을 일반 규칙처럼 씀 | 정의·규칙 문장("A는 B다", "~하지 않는다", "~해야 한다")이 이 글의 그림 표기·예제·코드에서만 성립하는데 범위 표시가 없다. CP 결정을 본문으로 옮긴 문장은 결정의 전제가 빠지지 않았는지 본다. 예제 값을 대입한 식(정답 0일 때의 미분)을 일반식처럼 쓰지 않았는지도 본다 | "이 글의 그림에서는", "이 예제는"처럼 범위를 붙이거나, 일반적으로 맞는 문장으로 바꾼다 |
| AP18 | 고치면서 넓어진 단정 | 막연한 문장을 구체적으로 고치거나, 표와 본문의 단정 정도를 맞추거나, 리뷰·에이전트의 수정안을 넣을 때 새 문장이 원래보다 강해졌다("아닐 수 있다" → "아니다", "다르다" → "에러가 나지 않는다"). 같은 글 앞에서 만든 예제(빈 입력, 다른 자료형, 다른 옵션 값 등)가 반례가 되는지 본다 | 새 문장을 같은 글의 예제로 실행해 반례가 없는지 확인한다. 맞출 때는 강한 쪽이 아니라 확인된 범위 쪽으로 맞추고, 조건("이 예제처럼 입력이 정수일 때는", "기본 옵션에서는")을 붙인다 |

AP15~AP18은 샘플 분석이 아니라 AI가 쓰는 글의 위험을 막으려고 추가했다.

## 근거 판정 (AP3, AP9, AP15)

출력이나 수치의 근거를 점검할 때는 다음 상태를 구분한다. 근거를 찾지 못한 것과 근거를 만든 것은 다르다.

| 상태 | 판단과 조치 |
|---|---|
| 본문에는 없지만 첨부 노트북이나 실행 기록에서 확인됨 | 문제 아님. 본문에 출력을 넣으라고 일괄 요구하지 않고, 독자에게 필요한 자리에 있는지만 본다 |
| 이용 가능한 자료에서 확인되지 않음 | "근거 확인 필요"로 보고한다. 지어냈다고 단정하지 않는다 |
| 실행하지 않은 예시 출력을 실제 실행 결과처럼 쓴 사실이 확인됨 | AP15. 지우거나 실제 실행 결과로 바꾼다 |
